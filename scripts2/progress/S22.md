# S22 — Resilience: wake lock, crash snapshot, host takeover

Issue: #45 · Branch: `main` · Status: **shipped**

## What shipped

The four things that decide whether this survives contact with a real staff
room.

- **Screen wake lock.** The phone holds one for as long as somebody is in a
  room, and releases it when the session ends.
- **Crash snapshot.** Room state is mirrored to one JSON file on every change
  and read back on boot. A SIGKILL thirty minutes in loses nothing.
- **Host takeover.** The first browser owns the room; a second sees it
  read-only, with every control inert and one live *Take over*.
- **Session reset.** *End the session* clears the room and opens a fresh one, so
  the activity can run twice in a day.

## Decisions taken

- **The wake lock fails silently.** iOS locks at thirty seconds by default —
  *shorter than the watch window* — so without this the room's screens go dark
  in the middle of every round. But token identity already covers a locked
  phone, so a browser without the API loses nothing but convenience, and an
  error about it would be noise during an activity. It is re-taken on
  `visibilitychange`, because a lock is dropped whenever the tab is
  backgrounded, which is exactly what a phone locking does.
- **The snapshot is written to a sibling and renamed.** A crash mid-write would
  otherwise leave half a file that will not parse on boot — the safety net
  causing the fall. A write failure is swallowed for the same reason: a room
  that cannot write its crash mat still runs.
- **A snapshot with no `hostToken` is ignored.** Restoring a room nobody was in
  would put a stale code on the projector, which is worse than starting clean.
- **The core guarantee is testable even though the file is not.** `server` and
  `snapshot` are shell and stay unit-untested, so what is asserted instead is
  the property the whole mechanism rests on: a mid-session room — silent round
  run, a latecomer, an opt-out, a spotlight open, a card spent — survives
  `JSON.parse(JSON.stringify(state))` unchanged, goes on reducing identically
  through five more events, and produces byte-identical views for every phone.
- **A second host gets its own token, not a share of the first one's.** Before
  this, a second `/host` connection was silently handed the same identity, so a
  facilitator with a laptop and a phone was driving from both without knowing.
  Now the second browser is registered as a host, sees the room exactly as it
  is with the controls greyed out, and takes it deliberately.
- **Host role is no longer enough to drive.** Every host-only event now also
  requires the token to be the one holding the room. `TAKE_OVER` is the single
  exception, and it is what a read-only screen is for.
- **`END_SESSION` is guarded in the core as well as the shell.** Everything else
  host-only is a control; this one throws the room away, and one guard on the
  far side of a socket is a thin place for that to depend on.
- **Ending a session invalidates every token by construction** — the state is
  replaced, so old phones are strangers rather than being remembered and
  refused. Nothing carries over: no barriers met, no passages used, no plan.

## Nothing is logged

Asserted mechanically rather than promised: the verify gate now scans every file
in `src/` for `console.*` and fails on anything beyond the single boot line,
which is also checked for the words that would make it a participant record.
The leak worth catching is the one added later by somebody debugging a session
at eight in the morning.

The snapshot holds names and tokens because it *is* the live room, but it is
overwritten rather than appended, never derived from, and deleted when the
session ends. It is a mirror, not a record.

## The harness found two things worth keeping

The mid-session crash test initially **passed vacuously**: it killed the server,
waited for the roster to look right, and the host's *pre-crash* view still
looked right, so a room that never came back would have scored green. It now
counts views received and requires every phone to have a genuinely new one.

And a stale snapshot from an earlier run on the same port made the next run's
facilitator arrive to a read-only view of somebody else's room. In the harness
that was a bug (fresh boots now clear the file); in production it is correct
behaviour, and it is exactly why *Take over* exists.

## Verified

312 unit tests: the JSON round trip of a genuinely mid-flight room, identical
reduction and identical views either side of it, no clock reading or duration
anywhere in the state; first claim owns the room, a second is read-only with a
takeover, takeover moving control both ways, neither host on the roster, and a
participant unable to claim or take it; ending a session emptying the room,
invalidating every token, and a fresh room opening straight afterwards with
nothing carried over.

Harness green at 1, 2, 5, 8 and 20 with the server **SIGKILLed mid-session** and
restarted on the same port: the room comes back with the same code, every phone
reconnects with the token it already held and receives a fresh view, and the
session carries on into the reveal. In the browser: a second facilitator device
seeing the room with *Start* and *End the session* greyed out and a live *Take
over*, and the first browser dropping to read-only the moment it was used.
