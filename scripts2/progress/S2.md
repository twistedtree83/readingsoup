# S2 — Connect hosting: Netlify site and Fly app

Recorded here by the runner during a GH↔graph cross-check: issue #25 was closed
on 2026-08-11 and the graph still said `passes: false`. The work was the

## What shipped

**One host, not two.** Live at **https://soup-readingsoup.fly.dev** — landing
page, solo mode, and `/host` for the projector, all from a single URL.
Auto-deploys from `main` via GitHub Actions with the verify gate in front of it,
sleeps when idle, pinned to a single machine.

## The decision, and why it went against the plan

The PRD split the static site (Netlify) from the realtime server (Fly) so the
solo demo would survive the server being asleep or undeployed. In practice that
means two addresses for one activity, and **a facilitator standing in front of a
room should have exactly one thing to say out loud**. A two-second cold start is
the better trade.

The static half still builds standalone (`bun run build`, `netlify.toml`) if a
separate static deploy is ever wanted, but nothing depends on it.

## What this means downstream

- The single-machine pin is load-bearing: room state lives in one process, so a
  second machine would be a second, empty room. [[S22]] (resilience, host
  takeover) inherits that constraint.
- `PUBLIC_URL` is what the QR encodes; the server cannot discover it behind the
  platform proxy.
