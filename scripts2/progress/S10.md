# S10 — Rooms and join: three roles, token identity, roster, QR

Issue: #33 · Branch: `sprint/soup-mvp` · Status: **shipped**

## What shipped

A Bun + Socket.IO server, one room at a time, three roles, a projected lobby with
room code and QR, and token identity that survives a locked phone.

`src/client/transport.js` makes the PRD's "one core, two transports" real: solo
runs the pure core in the browser behind a loopback, a room sends the same events
to a server running the same core. The renderer receives a `ClientView` either
way and cannot tell the difference.

## The wellbeing rule this slice had to get right

**The roster carries names only.** No roles, no counts split by role, nothing
derived from who chose to observe. The host view is projected to the entire room
at once, so anything role-shaped on it would disclose an opt-out to everybody
simultaneously — the exact thing the observer role exists to prevent. There is a
test named in capitals for this, and protocol-level verification confirms a
five-person room where the observer is indistinguishable.

## Three bugs found in verification, all real

1. **Both surfaces shared one `localStorage` key.** The phone presented the
   host's token and the server reconnected it *as the host*. This is not
   hypothetical: the PRD requires a facilitator to run the projector and their
   own phone side by side on one device for small groups, and both tabs share
   storage. Fixed by namespacing (`soup.token.host` / `soup.token.player`) and,
   belt-and-braces, by the server refusing to let a non-host `hello` adopt a
   host token.
2. **A reload dropped a joined participant back to the name prompt.** iOS locks
   at thirty seconds and suspends the socket, so a participant returns to this
   page repeatedly during one session — being asked "what should we call you?"
   in front of the room, mid-activity, is exactly the failure the token model
   exists to prevent. The server now returns `known` on identity so the client
   can distinguish a genuine resume from a stale token pointing at a dead room,
   and a stored token resumes silently.
3. **Opening `/host` a second time destroyed the live room.** A facilitator
   refreshing the projector, or a participant wandering onto the host URL, wiped
   the session and everyone in it. A room is now never destroyed by arrival: an
   existing room is adopted rather than replaced.

## Verified

Protocol-level, five participants including an observer: roster names only, no
role leak, participants see their own role and nobody else's, a locked phone
stays on the roster and reconnects by token with name and role intact, and a
host refresh preserves both room code and roster.

## Decisions taken

- **QR uses a dependency, deliberately.** A QR code is Reed-Solomon plus
  masking, and a subtly wrong hand-rolled encoder produces something that looks
  plausible and does not scan. With no decoder here to verify against, an
  unverifiable hand-rolled version would be worse engineering than a
  battle-tested library. "No client library, no CDN" is still honoured — the
  page receives finished SVG markup.
- **The Socket.IO client is served by the game server**, never a CDN, and is
  imported only when someone actually joins a room. The static site therefore
  keeps working with no server at all, which is the whole point of the split.
- **`PUBLIC_URL` is required for the QR.** The server sits behind a platform
  proxy and the join URL may point at the static site rather than at itself, so
  it cannot discover the hostname clients actually reach it on.
- **Disconnected participants are never removed** from state. Phones lock during
  every round; the participant is still in the room even when their socket is not.

## Follow-up fixes applied

**Headcount is now honest.** It counts who is *connected*, not who has ever
joined. This mattered more than it first looked: the facilitator reads that
number when deciding to start, and PRD mode selection picks solo/small/group
from participant count — a stale roster would have pushed a small session into
group mode. The roster still lists everyone, greyed when away, so a locked phone
keeps its place. Still a single total, never split by role.

**The Netlify deploy is scoped.** Publishing the repo root would have uploaded
`node_modules`, the test suite, the task graph and the PRD — 8.6MB instead of
88KB, with the whole harness public. `scripts/build-static.sh` assembles a
`dist/` containing only the site. "No build step" in the PRD means no bundler and
no transpiler; the client is still plain ES modules served exactly as authored,
and this is a file copy. Recorded here because it is a deliberate reading of a
PRD constraint, not an oversight.

**The projector degrades instead of blanking.** On a static deploy there is no
Socket.IO client to import, so `/host` threw and rendered nothing. It now says
what is missing and links to the tour. The PRD requires the site to work
completely with no server; a blank projector is the worst possible failure.

**Reducer effects are wired.** The shell was discarding them. Nothing consumes
effects yet, but leaving it would have handed S12+ a shell that looks connected
and is not.

Verified against a static-only server standing in for Netlify: `/host` shows the
offline screen, the room-code path degrades to "That room isn't running" with a
solo fallback, and the full six-condition tour runs from `dist/` with no server
at all.
