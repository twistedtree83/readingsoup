# S12 — Turn loop and private passage delivery

Issue: #35 · Branch: `main` · Status: **shipped**

## What shipped

The facilitator picks a reader from the roster. That person's phone receives the
passage. **Everybody else receives nothing** — no tokens, no render mode, no
passage — and is shown a watch-and-listen screen. The reader taps done, the
projector shows the passage cleanly, and *Next reader* returns to the roster.

Passage is unmangled in this slice; conditions arrive with the silent round.

## The load-bearing assertion

`no non-reader ever receives passage content` is now tested exhaustively: at 2,
5, 8 and 20 participants, across lobby / round / after-done / next-round, for
every role including a stranger with no place in the room. Every passage and
dictation prompt in the library is checked word by word against every view.

It holds because `view.viewFor` is the single path by which any client obtains
any data. The harness re-proves it on the wire at every size.

## Five bugs found, all real

1. **The turn loop did not loop.** The clean-passage slide was terminal — no way
   to start a second round. Added `END_ROUND`, so a single turn became a loop.
2. **A second `/host` arrival destroyed the room mid-round.** S10's guard only
   treated a room as live while it sat in the *lobby*, so the instant a round
   started, any new host connection wiped the session. Worse than the case S10
   fixed, because it lands mid-activity. A room is live from `hostToken`
   onwards, regardless of phase.
3. **A participant could join twice.** `hello` fires on every socket connect and
   the token was only stored when identity came *back*, so two rapid connects
   sent two null tokens and produced two people on the projector. The client now
   mints and persists its token *before* connecting, making every hello
   idempotent.
4. **A stale token stranded a participant in a nameless lobby.** The
   ask-for-a-name fallback fired correctly and was then painted over by the
   incoming view, leaving someone in no room at all — invisible to the
   facilitator and unable to be called on. Views are now suppressed until the
   person has actually joined.
5. **The reader saw "Which of these would make this easier?" above zero cards**,
   since dealing is S15. The prompt is hidden until a hand exists.

## Tokens stay off the projector

The host addresses participants by **roster position**, never by token — a token
is an auth credential, and putting one on the projector would let the
facilitator act as that participant. `rosterTokens(state)` resolves position to
token server-side, and a test asserts no participant token appears in the host
view.

## A note on method

Two silent failures cost real time and are worth recording:

- A `.replace()` whose target did not match is a **no-op**, and I used that
  pattern to restore a sabotaged file. The restore silently did nothing and the
  bug reappeared as a mystery — the unit suite could not catch it because
  `liveRoom` is server code. Edits now assert their target matched, and restores
  use git rather than `cp` from `/tmp`.
- The sim harness booted on a random port and treated *anything* answering as
  its own server. A stray unrelated process on 9091 meant a whole session was
  asserted against a stranger's service. It now refuses an occupied port and
  confirms the responder is actually this server.

## Verified

126 unit tests. Harness green at 1, 2, 5, 8, 20. In-browser: roster → announce
slide → reader gets the passage → non-reader gets the inverted watch screen with
no tokens → done → clean passage on the projector → *Next reader* → roster.
